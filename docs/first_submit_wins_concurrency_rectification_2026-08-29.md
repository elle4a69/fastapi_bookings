## Executive Summary

This remediation completes the total retirement of temporary booking holds and rectifies the concurrency guarantees of the first-confirmed-submission-wins booking model across both SQLite (default development/testing engine) and PostgreSQL (production engine).

Previously, the application attempted to enforce concurrency using pessimistic `with_for_update()` row locking on the `Provider` row combined with a unique constraint on `(provider_id, start_time)`. This model suffered from three critical vulnerabilities:
1. SQLite does not support row-level `FOR UPDATE` locks, making `with_for_update()` a no-op under the project's default database.
2. The index on `(provider_id, start_time)` failed to prevent overlapping bookings with offset start times (e.g. 10:15 vs 10:00) or buffer collisions (15-minute prep/cleanup windows).
3. Concurrent public and SMS submissions were prone to race conditions where two transactions passed the read-time overlap check simultaneously.

We rectified this architecture by introducing durable, discrete 15-minute slot allocations (`booking_slot_allocations`) with an atomic unique constraint on `(provider_id, slot_start)` spanning `[start - buffer_before, end + buffer_after)`. The entire booking creation, slot allocation, and outbox event dispatch occur within a single atomic database transaction. Any conflicting submission immediately encounters a database-level integrity error, rolls back cleanly, creates zero outbox events, and returns `HTTP 409 Conflict`.

## 1. Concurrency Vulnerabilities & Root Causes

| Defect | Mechanism | Root Cause & Failure Mode | Rectification Applied |
|---|---|---|---|
| **SQLite Pessimistic Lock Inefficacy** | `db.query(Provider).with_for_update()` | SQLite ignores `FOR UPDATE`; concurrent transactions proceeded concurrently to read availability. | Replaced application-level row locking with durable slot allocations backed by database unique constraint. |
| **Offset Overlap & Buffer Hole** | `uq_active_bookings(provider_id, start_time)` | Only protected exact identical `start_time` matches; allowed 10:15 to overlap 10:00 and ignored 15-minute buffer windows. | Slot allocations partition the entire booking window plus buffers into discrete 15-minute intervals. |
| **Hold Subsystem Remnants** | Webhooks & Diagnostics | Webhooks allowed registering `hold.created`, `hold.confirmed`, and `hold.expired`; diagnostics reported a `holds` module. | Removed all hold event types from `SUPPORTED_EVENTS` and purged `holds` from diagnostics schemas/routes. |
| **Passive Waitlist Safety** | Waitlist Engine | Risk of waitlists inadvertently claiming slots or holding calendar state. | Enforced waitlists as passive administrative records that create zero slot allocations. |

## 2. Architecture & Database Design

### 2.1 Discrete Slot Allocation Model (`BookingSlotAllocation`)

The `BookingSlotAllocation` model (`app/models/booking_slot_allocation.py`) provides physical representation for every 15-minute interval consumed by an active booking and its required buffers:

```python
class BookingSlotAllocation(Base):
    __tablename__ = "booking_slot_allocations"

    id = Column(Integer, primary_key=True, index=True)
    tenant_id = Column(Integer, ForeignKey("tenants.id", ondelete="CASCADE"), nullable=False, index=True)
    booking_id = Column(Integer, ForeignKey("bookings.id", ondelete="CASCADE"), nullable=False, index=True)
    provider_id = Column(Integer, ForeignKey("providers.id", ondelete="CASCADE"), nullable=False, index=True)
    slot_start = Column(DateTime(timezone=True), nullable=False)
    created_at = Column(DateTime(timezone=True), default=lambda: datetime.now(timezone.utc), nullable=False)

    __table_args__ = (
        UniqueConstraint("provider_id", "slot_start", name="uq_provider_slot_allocation"),
        Index("ix_slot_alloc_tenant_prov_start", "tenant_id", "provider_id", "slot_start"),
    )
```

### 2.2 Granularity & Interval Generation (`app/services/slot_allocation_service.py`)

- **Granularity:** 15 minutes (`SLOT_GRANULARITY_MINUTES = 15`).
- **Minimum Buffer:** 15 minutes (`DEFAULT_MIN_BUFFER_MINUTES = 15`).
- **Blocked Window:** `[booking.start_time - buffer_before, booking.end_time + buffer_after)`.
- **Generation:** Discrete `slot_start` timestamps generated by flooring the window start to the nearest 15-minute bucket and iterating every 15 minutes until `blocked_end`.

### 2.3 Single-Transaction Atomic Booking Engine

In `app/api/routers/public_bookings.py` and `app/api/routers/bookings.py`:
1. Validate client, service, provider eligibility, and business rules.
2. Instantiate `BookingModel`.
3. Generate and add `BookingSlotAllocation` rows covering the service duration and prep/cleanup buffers.
4. Execute `db.flush()`. If any slot is already occupied, the database throws `IntegrityError` on `uq_provider_slot_allocation`.
5. Allocate resource dependencies (if configured).
6. Create the `booking.created` outbox event.
7. Execute `db.commit()` in the single atomic transaction.
8. On exception / conflict: `db.rollback()`, zero outbox events are created, and `HTTP 409 Conflict` is returned with detail `"The requested time slot or buffer has just been booked. Please select another available time."`.

### 2.4 Cancellation and Rescheduling Lifecycles

- **Cancellation:** `release_allocations_for_booking(db, booking.id)` deletes all associated `BookingSlotAllocation` rows in the same transaction as setting `booking.status = CANCELLED`, instantly freeing all slots and buffers for new submissions.
- **Rescheduling:** `reschedule_allocations_for_booking(db, booking, new_start, new_end)` atomically clears old allocations, updates booking start/end times, generates new slot allocations, and flushes changes.
